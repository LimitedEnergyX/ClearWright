## 1. Purpose and scope

ALF (Automated Leap Frog) is a ClearWright-internal continuous-improvement subsystem. It observes how governed ClearWright runs succeed, fail, stall, retry, consume resources, and require operator intervention; converts evidence-bound observations into deduplicated, dynamically prioritized, durable improvement findings; and proposes testable governed-work specifications. The operator alone decides which findings become governed implementation work.

1. Structured run observations
2. Durable synthesized findings
3. Evidence and cryptographic hash binding
4. Deduplication with preserved lineage
5. Recurrence and cumulative-waste tracking
6. Tiered, transparent, versioned priority scoring
7. Root-cause confidence and blast-radius assessment
8. Regression detection, reopening, and escalation
9. Run Improvement Delta generation
10. Proposed governed-work specifications
11. Operator review and promotion controls
12. A minimal operator-usable view to inspect findings and approve, defer, reject, merge, or promote them

## 4. Three-layer model

Layer 1 - Immutable run observations. Facts captured from durable surfaces at run boundaries. Append-only, content-addressed, never edited, never deleted within Phase 1 retention. An observation that later proves wrong is countered by a new correcting observation that references it; the original stays.

Layer 2 - Durable synthesized findings. Mutable, versioned records synthesized from observations. Every mutation appends a new revision to an append-only per-finding history log with a revision hash chain; the head record is a pure function of the revision log. Findings change as evidence, recurrence, confidence, priority, and understanding change - with full audit.

Layer 3 - Governed improvements. Only the operator promotes a finding toward implementation. Promotion produces a governed-work specification document, never a work item, never authority. Any actual implementation runs through the normal ClearWright governed workflow (operator authority, clearance, plan council, gates, verification, closure).

Boundary rule: data flows upward only by reference (observations referenced by findings, findings referenced by specifications). Nothing in a higher layer rewrites a lower layer.

## 5. Immutable run observations

Storage: QUEUE_ROOT subtree alf/observations/, one JSON file per observation named obs-<identity-hash-16>.json, plus a tamper-evident index alf/observations/index.jsonl (one line per observation: observation_id, sha256 of the observation file bytes, captured_at, run_id, kind, prev_line_sha256, line_sha256 - the per-line hash chain of section 8). Files are written with the existing atomic tmp-then-replace pattern and are never modified afterward; index appends run under the single-writer lock with flush-before-release (section 8 write discipline).

Collision refusal: on writing an observation whose id already exists, the writer compares the FULL canonical identity tuple, not the truncated id. Identical tuple = verified no-op. Same truncated id with a DIFFERENT tuple = the write is REFUSED and reported as a Tier 1 durable-record-integrity finding candidate (id_collision); it is never treated as an ordinary existing-file condition.

Observation identity (deterministic, single scheme): observation_id = "obs-" + first 16 hex of sha256 over the canonical serialization (section 8) of the identity tuple {kind, subsystem, work_item_id, thread_id, council_id, gate_id, summary, source_identity, metrics}, where source_identity is the list of {ref, sha256} pairs ONLY, canonically ORDERED by (ref, sha256) ascending - so the same evidence discovered in any capture order yields the same observation_id (pinned by fixture) - and the archival metadata fields (role, archived_location) are recorded on the evidence objects but are EXCLUDED from identity, so archival changes never change an observation's id. captured_at, run_id, capture_method, and capturing_actor are recorded fields but are EXCLUDED from identity, so re-capturing the same facts yields the same id and is a verified no-op (the writer confirms byte-equality of the identity fields and skips). Different metrics or different source facts produce a different identity and therefore a distinct observation. The filename, the index key, and every evidence reference use this same observation_id.

Observation schema (alf_record_version 1):
- observation_id: string, obs-<identity-hash-16> (deterministic; see identity rule above)
- captured_at: UTC ISO timestamp (recorded; excluded from identity)
- run_id: string binding the capturing run (work item id plus capture sequence)
- work_item_id, thread_id, council_id, gate_id: optional subject bindings
- kind: enum - run_started, run_completed, run_closed, council_round, council_outcome, reviewer_attempt, dispatch_failure, gate_created, gate_resolved, lifecycle_event, complete_refusal, close_recorded, operator_intervention, resource_usage, executor_note
- subsystem: enum - envelope_classification, work_item_lifecycle, council_engine, reviewer_gpt, reviewer_codex, egress_guard, dispatch_lane, queue_store, gates, server_lifecycle, operator_ui, cli, executor_process, other
- summary: short plain-language statement of the observed fact (no secrets, no personal content; same hygiene rules as council packets)
- source_refs: array of evidence objects {ref, sha256, role, archived_location} in the section 8 form (single source of truth; no parallel arrays)
- metrics: optional object - operator_minutes, execution_delay_seconds, token_estimate, gpt_tokens_actual_in, gpt_tokens_actual_out, api_attempts, tool_attempts, council_attempts, invocations. In hashed structures this object is present-as-null when absent (never an omitted key); when present, every listed key is present with JSON null for any absent sub-value, per the section 8 canonical representation table - so the canonical bytes are deterministic.
- capture_method: enum - cli_explicit (alf-observe invocation), run_boundary (emitted by the run wrapper at start and terminal events), backfill (operator-authorized historical import)
- capturing_actor: string (executor identity)

Capture design (Phase 1): observation capture is invocation-driven, not a daemon. A new CLI verb (section 18, ALF-CLI) reads the existing durable surfaces for a named run or work item and emits observations deterministically; re-running capture for the same facts is idempotent under the identity rule above. No polling process, no background service.

Immutability enforcement (tamper-evident, application-level): the writer refuses to write an observation file that already exists with different identity-field bytes; the index receives appends only; a verification helper re-hashes files against the index and reports any divergence as a Tier 0 durable-record-integrity event. The protection claim and its boundary are stated precisely in the section 8 threat model (these records are tamper-EVIDENT through hashes and chained anchors, not physically append-only on a local filesystem).

Run-occurrence layer (so later-run recurrences are never dropped): the fact observation above is deduplicated by identity and is intentionally run-agnostic (its own run_id/captured_at record only the FIRST capture, as provenance). ALF ALSO records, for EVERY capture, a durable per-run occurrence in alf/observations/occurrences.jsonl (per-line hash chained like the ledger and index, first-line sentinel per section 8). One line per occurrence: {occurrence_id = sha256-16 over canonical {observation_id, run_id}, observation_id, run_id, captured_at, capture_method, capturing_actor, metrics, prev_line_sha256, line_sha256}. Occurrence writes are idempotent per occurrence_id (a re-capture in the SAME run is a verified no-op), but a NEW run capturing the same facts appends a NEW occurrence line even though the fact observation is a no-op dedup - so every governed run that observed a fact has its own durable run_id-bearing record. ALL run-scoped accounting - recurrence detection, occurrence_count, affected_run_count, cumulative-waste attribution, and Run Improvement Delta run-membership - consumes the OCCURRENCE records (occurrences whose run_id equals the run), NEVER observation.run_id; findings still cite the fact observation_id for evidence. Each occurrence append is written inside the operation-journal transaction (section 8) with its own attribution-ledger line, so it is idempotent and crash-safe end to end.

- council:<council-id> - a council record; council-round:<council-id>#<n> - one round record; council-outcome:<council-id>
- gate:<gate-id>; invocation-log:<UTC-date>#<line-span>; lifecycle:<UTC-timestamp>; agent-event:<event-id>
- repo-file:<repo-relative-path>#<commit> - committed repository content
- alf-observation:<observation-id>; alf-finding:<entry-id>#rev<n>
- work-record:<file-name> - a durable planning or result record in the runtime work directory

Evidence entry form (one-to-one by construction): evidence_references is an array of objects {ref, sha256, role, archived_location} where ref uses the typed grammar above, sha256 is computed over the exact referenced bytes at capture time (whole file for record references; the exact byte span for log spans; the committed blob for repo-file references), role is one of defining_authority | observed_occurrence | verification | correction, and archived_location is optional. The flat mandatory field evidence_hashes is DERIVED by the writer from the objects (same order) and validated for exact length and order parity on every revision; the objects are the single source of truth. A revision that adds a reference without its hash, or whose derived array diverges, is rejected by the writer. Duplicate refs are normalized (one object per distinct ref; a re-capture updates role or archived_location only through a new revision).

Hash verification is re-runnable: a verifier command re-hashes every reference and classifies each as verified (bytes match), archived_unavailable (source no longer present at the recorded location; capture-time hash stands as evidence), or divergent (bytes exist and differ - which itself becomes a Tier 0 durable-record-integrity observation).

Canonical serialization (applies to every hashed artifact - observation identity tuples and files, finding records, revision lines, index and ledger lines, tier decisions, model input vectors, delta records): UTF-8, JSON with sorted keys, compact separators (comma and colon, no spaces), ensure_ascii off, exactly one trailing newline per record line, byte spans referenced by exact offsets. Two implementations following this section must reproduce identical hashes.

Canonical data-representation table (field by field; hashed records contain ONLY these forms, and the writer refuses any non-integer JSON number in a hashed record):
- Confidence-like values (root_cause_confidence, merge-proposal confidence, automated-judgment confidence): fixed two-decimal STRINGS, "0.00" through "1.00", in every stored and hashed record; numeric rendering happens only in display surfaces.
- Counters and attempts (occurrence_count, affected counts, api/tool/council attempts, invocations): JSON integers.
- cumulative_operator_minutes: integer minutes, rounded up at capture. cumulative_execution_delay: integer seconds, rounded up. cumulative_token_estimate and actual token fields: integers.
- Scores, tiers, blast-radius ranks, waste bands, effort points: integers. Leverage: two-decimal string, display-derived, never hashed as a number.
- Timestamps (captured_at, generated_at, at, computed_at, first_seen_at, last_seen_at, surfaced_at): UTC ISO-8601 strings with Z suffix, microsecond precision.
- Identifiers, enums, refs, hashes: strings from their defined vocabularies. Booleans: JSON booleans. Absent optional values: JSON null (never omitted keys in hashed structures).
Cross-language serialization fixtures with known hashes are part of the P1a test set.

Operation journal (transactional synthesis with durable staged payloads; the exactly-once mechanism): alf/journal/journal.jsonl, append-only under the writer lock with the same per-line hash chain as the ledger, plus an immutable staging area alf/journal/staged/<op_id>/. Every synthesis operation (create finding, recurrence update, regression reopen, waste attribution, merge confirmation, disposition, delta generation) runs as:
1. Derive every staged payload COMPLETELY (all timestamps, revision numbers, predecessor hashes, anchors, and deterministic ids fixed now) and write each payload BYTE-EXACTLY to a content-addressed staging file alf/journal/staged/<op_id>/<n>-<content-sha256-16>; fsync each staging file and the staging directory.
2. Append op_begin {op_id, operation_kind, staged_writes, at, prev_line_sha256, line_sha256}; fsync the journal file. Each staged_writes entry is {target_path_rel, staged_file, content_sha256, write_kind (append_line | replace_file)} PLUS, for replace_file, an EXPECTED-OLD binding captured at derivation time: expected_mode (absent | file_exists) and, when file_exists, expected_existing_sha256 (the sha256 of the target's pre-transaction bytes); PLUS, for append_line only, the predecessor binding captured at derivation time: expected_prev_line_sha256 (the line_sha256 of the target's current last line, OR of the immediately preceding staged append to the SAME target when a transaction stages several appends to one target, or the first-line sentinel below for an empty target) and expected_chain_position (the 1-based line number the staged line will occupy). op_id = sha256-16 over canonical {operation_kind, primary attribution_id or subject ids, ordered staged content hashes}; on an existing op_id the writer compares the FULL canonical operation identity - identical is a no-op resume, same-short-id different-identity is REFUSED and halts (same collision rule as observation ids). The journal's own op_begin and op_commit lines carry the standard chain fields (prev_line_sha256, line_sha256 over the canonical line minus its own hash field). The staged-write list is OPERATION-SPECIFIC and dependency-ordered, and EVERY committed transaction's list ALSO includes the mandatory expected-head checkpoint replace_file (alf/meta/expected-heads.json) as its final staged write (a delta generation stages its snapshot, delta file, ledger lines, and the checkpoint; a recurrence update stages its ledger line, revision line, head, and the checkpoint; nothing else is encoded). Crash/recovery coverage asserts the checkpoint staging for recurrence and delta operations.
3. Apply the staged writes in listed order, copying staged bytes only (appends as whole fsynced lines; file replacements via the existing atomic tmp-then-replace plus fsync).
4. Append op_commit {op_id, at, prev_line_sha256, line_sha256}; fsync. Staging files are deleted only after op_commit is durable (and after recovery verification when recovery ran).
ACYCLIC ANCHORING (the rule that makes the hash graph non-circular): every anchor value a staged payload carries - the delta anchors block (section 17) and the expected-head checkpoint - binds the PRE-transaction heads: the journal head and each chained-file head as of BEFORE this operation's op_begin, all durable and known at staging time in step 1. No staged payload ever references its own op_begin, op_commit, or any post-commit head. The derivation order is strictly forward and acyclic: pre-transaction heads -> staged payload bytes -> content hashes -> op_id -> op_begin line -> applied writes -> op_commit line, each value depending only on values fixed earlier. A transaction's own op_begin and op_commit records are protected after the fact two ways: by the journal's internal per-line hash chain, and by the NEXT delta, whose pre-transaction journal-head anchor includes this transaction's op_commit. Every committed operation is therefore eventually anchored by a later delta; only operations since the most recent delta rely on the journal line chain alone (the honestly-bounded window in the section 8 threat model).
Readers treat data reachable only from an uncommitted operation as pending. Startup and alf-verify recovery consult ONLY the journal and the staged bytes, never re-deriving from mutable current state. Recovery is split by write_kind:
- replace_file: FOUR-WAY recovery against the expected-old binding, so a normal crash BEFORE the replacement (the old valid file still present) recovers instead of halting - live bytes == staged bytes: already applied, stays; live bytes == expected_existing_sha256 (the captured pre-transaction bytes): the replacement had not been applied, so write the staged bytes; target absent AND expected_mode was absent: write the staged bytes; ANY other state (live bytes are neither the staged nor the captured expected-old bytes, or the target is absent when file_exists was expected) is divergent and fails closed (report, halt).
- append_line: LINE-LEVEL, predecessor-anchored, and ORDERED PER TARGET - a transaction may stage more than one append_line to the SAME target; those staged appends form an ordered sequence in which each entry's expected_prev_line_sha256 is the line_sha256 of the immediately preceding staged append to that same target (or the target's current last line, or the first-line sentinel for an empty target) and its expected_chain_position increments accordingly. On recovery a target's staged appends are processed IN ORDER: each is treated as ALREADY APPLIED only when it is present at exactly its expected_chain_position with its recorded line hash and the chain around it intact (recognizing an already-applied PREFIX of the sequence); the first not-yet-present append is appended EXACTLY ONCE when the target's last line equals its expected_prev_line_sha256 at position expected_chain_position minus one, and each remaining append follows in order (whole-target equality is never used for appends - a JSONL target with prior lines never equals one staged line); ANY other parseable state (wrong line at the expected position, missing predecessor, a gap, or a chain that contradicts the binding) fails closed (report, halt).
After all staged writes verify or apply, op_commit is appended. Replay therefore converges byte-identically and can neither double-count nor lose an attribution. A crash BEFORE a durable op_begin leaves only orphan staging files, which recovery deletes (no dependent write can exist yet by ordering). An operation that cannot be completed (missing or corrupt staged bytes) HALTS ALL FURTHER ALF SYNTHESIS fail-closed until operator intervention and is reported as a Tier 1 durable-record-integrity finding candidate with the exact op_id.
Torn-tail rule (all chained JSONL files): a final PARTIAL line (invalid JSON with no terminating newline) is demonstrably torn - it is archived verbatim to a quarantine record, then truncated, and the chain resumes from the last valid line; a PARSEABLE line that breaks the hash chain is NOT repairable - fail closed, halt ALF synthesis, report. Crash-test matrix: a kill between every adjacent step above (payload staging, staging fsync, op_begin append, op_begin fsync, each applied write, op_commit), plus the append_line-specific matrix - crash BEFORE the append, crash AFTER the append but before its fsync, crash after the fsync but before op_commit, duplicate replay of a recovered operation, missing predecessor (target shorter than the binding expects), a wrong line at the expected position, and a MULTI-APPEND-TO-ONE-TARGET operation crashed after an applied prefix (recovery recognizes the prefix and completes only the remaining ordered same-target appends exactly once) - each followed by recovery that converges byte-identically or fails closed exactly as specified.

Write discipline: all ALF mutations run under the existing ClearWright single-writer lock. JSONL appends are written whole-line, flushed to disk before the lock is released; head files (finding heads, delta files, model files) are written with the existing atomic tmp-then-replace pattern (with the Windows sharing-violation retry already shipped in the queue writer). A torn or interleaved append is therefore excluded by the lock, and a crash mid-append leaves at most one incomplete final line, which the reader detects (invalid JSON line) and the verifier reports. Named Windows durable-write primitives: each staged file, JSONL append, and replaced head file is flushed with os.fsync (FlushFileBuffers on Windows) before the writer lock is released, and every file replacement fsyncs the replacement temporary file (FlushFileBuffers) BEFORE the os.replace and then uses os.replace (atomic on Windows via MoveFileEx with replace-existing). Windows provides no portable directory-fsync, so directory-entry durability is NOT assumed; the durability guarantee is therefore NARROWED and fail-closed - after a normal process crash the journal plus staged bytes recover deterministically, and under host power-loss a staged file that a committed op_begin references but that is absent on disk (its directory entry not yet persisted) is treated as an incomplete operation that HALTS synthesis and fails closed (Tier 1), never proceeding on partial state.

Attribution ledger (idempotency authority for synthesis): alf/attributions/ledger.jsonl, append-only under the same lock, per-line hash chained (each line carries prev_line_sha256 and line_sha256 over the canonical line minus its own hash field; the observation index, the journal, and finding histories use the same chaining; the FIRST line of every chained file uses the sentinel prev_line_sha256 of sixty-four zero hex characters, and first-line cases for every chained file are pinned by P1a fixtures). One line per attribution: {attribution_id = sha256-16 over canonical {occurrence_id, entry_id, attribution_type} - occurrence_id encodes {observation_id, run_id}, so the SAME fact attributed in two different runs yields two DISTINCT attributions, counted exactly once per run - occurrence_id, observation_id, entry_id, attribution_type (initial_evidence | recurrence | regression | waste | delta_report), at, run_id, prev_line_sha256, line_sha256}. Every counter update, recurrence link, regression reopen, waste accumulation, and delta line item is written inside an operation-journal transaction (above) together with its ledger line; an attribution whose id already exists is a verified no-op (nothing increments twice). Re-running synthesis over the same occurrences is therefore idempotent end to end, including across crashes. The ledger is the authoritative answer to what has been counted.

Threat model (explicit, honest boundary): ALF integrity protection is application-level and tamper-EVIDENT, not physically append-only and not externally anchored WORM storage. Detected intrinsically (per-line chains): in-file MUTATION, REORDERING, and NON-TERMINAL DELETION break the line chain and are reported with the first broken position. NOT detected by the chain alone: VALID TERMINAL TRUNCATION - removing one or more whole trailing lines leaves a prefix that is still a valid chain. ISOLATED terminal truncation - truncation of a chained file while a newer committed checkpoint still authenticates the pre-truncation head - is detected by EXPECTED-HEAD CHECKPOINTS: alf/meta/expected-heads.json, a record OUTSIDE the chained files (atomic tmp-then-replace), refreshed inside EVERY committed ALF operation-journal transaction (not only delta generation). It records, for each chained file, the PRE-transaction head line_sha256 and line count (the heads as of before this operation's own writes - acyclic, known at staging time), so the undetectable-truncation window is bounded by the most recent COMMITTED operation, not the most recent delta. The checkpoint is JOURNAL-AUTHENTICATED: each refresh is a replace_file staged write in that transaction's op_begin staged_writes, so its content_sha256 is committed in the durable journal chain. alf-verify locates the LATEST COMMITTED checkpoint staged-write in the journal and verifies the live expected-heads.json bytes against that committed content_sha256 BEFORE trusting the checkpoint; a checkpoint that is missing, replaced, stale, or divergent from its committed journal record FAILS CLOSED - an isolated local mutation of expected-heads.json to conceal a truncation no longer passes, because the mutated bytes will not match the committed staged-write hash. The verifier then checks each chained file against the AUTHENTICATED checkpoint by ANCESTRY PROOF, not a count-only comparison: it validates the complete live line chain and requires that the live line at the checkpoint's recorded line_count position has EXACTLY the checkpoint's recorded head_line_sha256 (an empty-file checkpoint uses the sixty-four-zero-hex sentinel and requires an empty live file); only suffix lines beyond that position are permitted. A recorded head that is missing, different, or not present at its recorded position in the live chain is an integrity failure (Tier 0) - so a replacement by a separately valid, internally hash-chained history of equal-or-greater length cannot evade detection. Truncation of lines written AFTER the latest committed checkpoint is explicitly reported as an UNDETECTABLE WINDOW (bounded by checkpoint time), never implied to be covered. Detected by chained anchors: wholesale replacement of a chained file after the first delta exists - each Run Improvement Delta carries an anchors block (schema in section 17) computed at first generation, and each delta records the previous delta's anchor-block sha256, forming a self-referential chain; replacing history without forging every subsequent delta in that chain breaks it and is reported (no existing record shape changes; the delta chain is self-contained via prev_delta_anchors_sha256). Integrity findings from these detections carry tiers consistent with this boundary: chain breaks and checkpoint-detected truncation are Tier 0 durable-record-integrity events; an undetectable-window report is advisory (it states the boundary, it does not claim an event). NOT defended (Phase 1, stated honestly): a COORDINATED TERMINAL ROLLBACK - an attacker who truncates the journal and the changed chained files back to a prior internally-consistent state AND restores the older expected-heads.json that the now-truncated journal still authenticates - passes verification, because every artifact is a valid earlier committed prefix and no hash is forged. The local checkpoint/delta design detects isolated mutation, reordering, non-terminal deletion, and isolated truncation while a newer committed checkpoint remains, but CANNOT detect a coordinated rollback to any prior locally-valid state; alf-verify reports that case as an explicit undetectable-coordinated-rollback boundary, never a false integrity success. Closing this gap requires an independently durable EXTERNAL MONOTONIC ANCHOR (for example a hash-bound record in the existing durable communications/summary system whose own rollback is independently detected) - a Phase-2 option, NOT claimed in Phase 1. Also NOT defended: an attacker with full filesystem write access who consistently rewrites all ALF records, checkpoints, deltas, and referencing run records - outside the supported threat model and stated as such.

## 9. Finding deduplication

Deduplication is proposal-based, never silent for protected classes:
- Candidate key: (subsystem, failure_class, normalized root-cause signature). Normalization and similarity are fixed by a versioned artifact alf/meta/dedup-policy-v1.json: ASCII-lowercase the root_cause text; split on every non-alphanumeric character except underscore (identifiers with underscores and digits survive as single tokens); drop the exact stopword list enumerated in the artifact; the signature is the sorted unique token set. Exact key match proposes duplicate_of with confidence "0.90"; Jaccard similarity of token sets at or above 0.80 proposes with confidence "0.80"; at or above 0.60 proposes with confidence "0.60"; below 0.60 no proposal. The dedup-policy version is stored with every proposal, and policy changes require a new artifact version.
- A proposed merge is a pending relationship on the newer entry (duplicate_of, proposed, confidence, rationale). The operator confirms or rejects it in review. On confirmation the newer entry's status becomes MERGED, meaning deduplicated into another ALF finding (not a Git or code merge); its occurrence and waste counters fold into the surviving entry; both entries record the supersession_lineage pair; the merged entry stays readable forever.
- Silent-merge prohibition: findings whose failure_class or impact axes touch security, privacy, authority integrity, or durable-record integrity are never auto-merged; the merge proposal renders prominently and waits for the operator.
- Auto-accept threshold: none in Phase 1. Every merge is operator-confirmed. (Conservative start; a later authority may loosen.)

## 11. Recurrence detection

- Every synthesis pass matches new OCCURRENCES (per-run observation records, section 5) against existing findings by the deduplication key before creating anything new. A match updates last_seen_at, occurrence_count, affected_run_count (counted over distinct occurrence run_ids), affected_work_item_count, and the cumulative waste counters, and appends a recurrence_of relationship from the triggering occurrence - every such update written together with its attribution-ledger line (section 8), so a re-run of synthesis over the same occurrences changes nothing, while the SAME facts recurring in a LATER run (a new occurrence bearing a new run_id) is correctly counted as one additional recurrence and one additional affected run for that finding.
- Recurrence never lowers priority. A recurrence while status is RELEASED or MONITORING is a regression (section 12), not a plain recurrence.
- Recurrence of a DEFERRED or ACCEPTED_RISK finding re-raises it into OPERATOR_REVIEW at the next delta with the recurrence evidence attached (the operator sees that the accepted risk is recurring; the disposition is not silently changed).
- The conservative excess-deliberation detector (Finding ALF-0002, section 21) is recurrence-driven: it reports only when the same entities and candidate decisions recur with no new tool evidence, unchanged authority, unchanged durable state, and unchanged constraints while tokens and elapsed time increase without execution progress - and its output is advisory only.

## 12. Regression handling

When a released or monitored issue recurs:
1. Reopen the ORIGINAL finding (status RELEASED or MONITORING back to PRIORITIZED; never a new low-priority duplicate).
2. Link the previous correction (implementation_work_item_id, released_version) and the previous verification_evidence.
3. Link the new run and the new evidence (references plus hashes).
4. Update occurrence_count and affected_run_count.
5. Re-score priority under the current model version and enforce the TIER-AND-SCORE FLOOR mechanically (a floor on this finding's own tier and score; NOT a claim about ordinal rank relative to other findings, which may legitimately move): when a finding first reaches RELEASED, the writer persists release_baseline = {tier, score, priority_model_version, at}; a reopened regression's effective tier is min(new_tier_number, baseline_tier_number) (numerically lower tier wins, Tier 0 lowest) and, when the effective tier equals the baseline tier, its effective score is max(recomputed_score, baseline_score_mapped) where baseline_score_mapped is the baseline score when the model version is unchanged, or the baseline input vector re-evaluated under the current model version when the model was upgraded (the stored input vector makes this deterministic). The regression escalation term of section 15 applies on top. Both the recomputed and the floored values are stored in the tier_decision record, so the floor application is itself reproducible.
6. Classify the reopening as regression_of in related_entries and set failure_class accordingly if the recurrence reveals a broader class.
7. Surface the regression in the next Run Improvement Delta and in operator review as a distinct regressions group.

## 13. Cumulative waste accounting

Per finding, monotonically non-decreasing counters, updated only from OCCURRENCE metrics (each per-run occurrence, section 5, carries that run's metrics; never estimated retroactively): cumulative_operator_minutes; cumulative_execution_delay (seconds); cumulative_token_estimate (plus actual provider-reported tokens when the surface records them); cumulative_api_attempts_wasted; cumulative_tool_attempts_wasted; cumulative_council_attempts_wasted. Attribution rule: an occurrence's metrics are attributed to a finding only when the occurrence is linked to it (recurrence, regression, or initial evidence), and every attribution is recorded exactly once in the attribution ledger (section 8) keyed by occurrence_id - a metrics contribution without a fresh ledger line is refused, and an existing ledger line makes the contribution a no-op, so totals can never double-count across re-runs, while a later run's occurrence of the same fact contributes exactly once for that run. Waste totals are display inputs and scoring inputs (section 15) and appear in every Run Improvement Delta as deltas plus running totals.

## 14. Hard priority tiers

A hard tier is assigned before any numeric score and is never reduced by effort:
- Tier 0: active or plausible authority bypass; privacy exposure; credential exposure; sensitive-data egress; destructive-action risk; unauthorized mutation; durable-record corruption; production ownership conflict.
- Tier 1: authority-integrity defects; durable-record-integrity defects; correctness failures; operational reliability failures; stale or misleading state; broken recovery; repeatable work blockers; council, queue, lifecycle, or deployment failures.
- Tier 2: operator time; execution delay; unnecessary councils; unnecessary retries; repeated tool calls; token, API, and compute waste; poor diagnostics; excessive deliberation without new evidence.
- Tier 3: clarity; user experience; documentation; maintainability; nice-to-have improvements.

Display rules: priority (tier plus score), estimated_effort, and leverage are displayed separately; effort never changes tier or score; visible critical findings are never capped; work-in-progress limits apply only to active implementation and planning states, never to visibility.

Deterministic tier assignment (versioned tier policy): tier assignment is mechanical, not prose judgment. The versioned model file (section 15) carries tier-policy-v1: an ordered list of predicates over structured finding inputs, evaluated top down, first match wins, default Tier 3. Structured inputs added for this purpose (recorded on the finding and in every tier decision): risk_activity (active | plausible | historical), exposure_class (none | privacy | credential | sensitive_egress), mutation_class (none | unauthorized_mutation_risk | destructive_action_risk), record_integrity_class (none | corruption_risk | corruption_observed), ownership_conflict (boolean). tier-policy-v1 predicates: Tier 0 when risk_activity in (active, plausible) AND (exposure_class is not none OR mutation_class is not none OR record_integrity_class is not none OR ownership_conflict); Tier 1 when authority_integrity_impact >= 2 OR durable_record_integrity_impact >= 2 OR failure_class in (authority_bypass_risk, durable_record_integrity, correctness, operational_reliability, stale_state, broken_recovery, work_blocker, council_failure, queue_failure, lifecycle_failure, deployment_failure); Tier 2 when failure_class in (operator_time, execution_delay, resource_waste, poor_failure_reporting, excess_deliberation) OR operator_time_impact >= 2 OR execution_delay_impact >= 2 OR token_api_compute_impact >= 2; Tier 3 otherwise. Every ranking revision persists a tier_decision record: {tier_policy_version, input_vector (all predicate inputs), matched_predicate, tier, computed_at} - identical inputs always reproduce the identical tier, offline. The predicate inputs are AUTHORITATIVE in tier_decision.input_vector; the finding mirrors them for display only.

## 15. Versioned scoring methodology

Model file: alf/meta/priority-model-v1.json (versioned; every ranking decision stores priority_model_version plus the exact inputs and the computed score, so any ranking is reproducible offline).

priority-model-v1 (transparent formula):
- Inputs: the seven impact axes (each 0 to 3), blast_radius rank BR (single_event=0 up to external_or_public=7), occurrence_count OC, regression flag RG (0 or 1), cumulative waste bands WB (0 to 3, from banded thresholds on the waste counters recorded in the model file).
- base = 4*security_impact + 4*authority_integrity_impact + 4*durable_record_integrity_impact + 3*reliability_impact + 2*operator_time_impact + 2*execution_delay_impact + 1*token_api_compute_impact
- radius_term = 2 * BR
- recurrence_term = 2 * min(OC - 1, 10)
- regression_term = 12 * RG
- waste_term = 2 * WB
- score = base + radius_term + recurrence_term + regression_term + waste_term (integer; higher is more urgent; ordering within a tier only - tier always dominates).
- Leverage (displayed separately, never part of score): leverage = score / max(estimated_effort_points, 1) with effort points from a small enum (1, 2, 3, 5, 8).
- Every stored ranking decision records: entry_id, model version, tier_policy_version, the full input vector (impact axes, blast radius, occurrence, regression flag, waste bands, and the tier predicate inputs of section 14), matched tier predicate, score, tier, any regression floor application (recomputed and floored values), computed_at, and the triggering observation or revision. The model file also fixes the exact waste-band thresholds. Identical stored inputs reproduce identical tier and score offline.

## 16. Operator review and promotion controls

Primary lifecycle: OBSERVED -> TRIAGED -> MERGED (dedup terminal) or PRIORITIZED -> OPERATOR_REVIEW -> APPROVED_FOR_PLANNING -> WORK_ITEM_CREATED -> IN_PROGRESS -> VERIFICATION -> RELEASED -> MONITORING -> CLOSED. Additional dispositions: ACCEPTED_RISK, DEFERRED, REJECTED, SUPERSEDED, NOT_REPRODUCIBLE.

Complete legal transition table (structural, enforced by the writer; any transition not listed is refused with the exact reason):
- OBSERVED -> TRIAGED: automated (synthesis). TRIAGED -> MERGED: operator-only (merge confirmation). TRIAGED -> PRIORITIZED: automated (scoring completes; tier_decision persisted).
- PRIORITIZED -> OPERATOR_REVIEW: automated and disposition-free - the finding is SURFACED for review when it first appears in a Run Improvement Delta or an operator listing; entering OPERATOR_REVIEW records only surfaced_at and changes no judgment field. Re-scoring while in OPERATOR_REVIEW is permitted (automated) and never leaves the state.
- OPERATOR_REVIEW -> APPROVED_FOR_PLANNING: operator-only, and additionally gated by the promotion elements below.
- OPERATOR_REVIEW -> DEFERRED | REJECTED | ACCEPTED_RISK | SUPERSEDED | NOT_REPRODUCIBLE: operator-only dispositions. DEFERRED requires deferral_reason and review_date. Recurrence of DEFERRED or ACCEPTED_RISK re-surfaces into OPERATOR_REVIEW automatically (section 11) without changing the recorded disposition history.
- APPROVED_FOR_PLANNING -> WORK_ITEM_CREATED -> IN_PROGRESS -> VERIFICATION -> RELEASED -> MONITORING -> CLOSED: recorded by REFERENCE only, mirroring the normal governed workflow's own records (implementation_work_item_id, released_version, verification_evidence); ALF never creates or advances the underlying governed work. RELEASED persists release_baseline (section 12). RELEASED or MONITORING -> PRIORITIZED: automated regression reopen (section 12).
- Regression reopen, recurrence updates, and merge PROPOSALS are automated; merge CONFIRMATION is operator-only.

Operator-message binding (all operator-only transitions, CLI and UI identically): the disposition command references a durable INBOUND operator message that (a) exists in the communications store, (b) has role operator and direction inbound, (c) was created AFTER the finding revision it disposes, (d) names the entry_id (or the merge pair), and (e) has not been used for any prior ALF disposition - one disposition per message id, so replay is refused. The consumed message id is recorded on the disposition revision (same authority pattern as the existing close and grant-proceed commands). No operator message, no transition.
- APPROVED_FOR_PLANNING gate (all required): defined permanent_resolution; objective_acceptance_criteria; required_regression_tests; evidence references plus hashes INCLUDING at least one observed_occurrence evidence entry (defining-authority evidence alone seeds a finding but does not qualify it for planning approval); an understood root cause (root_cause_confidence at or above "0.50") or an explicit investigation requirement recorded instead; known dependencies and blockers. The writer refuses the transition when any element is missing.
- Mirror-transition actor and reconciliation (WORK_ITEM_CREATED through CLOSED): the synthesis pass (automated) writes mirror updates by READING the governed workflow's own durable records (envelopes, summaries, clearance records). Binding proof: a promoted specification records its spec id; the operator includes that spec id in the governed work item's envelope text when creating the implementation work; the mirror accepts implementation_work_item_id only when the referenced envelope cites the spec id. A missing, contradictory, or non-citing external record NEVER advances the mirror - the finding is flagged items_requiring_operator_review with reason external_record_mismatch and waits for the operator.
- Prominence rules in review: root_cause_confidence below "0.50", low-confidence merge proposals, and any Tier 0 entry render at the top with explicit markers. Regressions render as their own group. Authority-seeded findings (authority_seeded true) are visibly marked until observed-occurrence evidence attaches.
- The promote action = the operator's APPROVED_FOR_PLANNING disposition (message-bound as above) PLUS a state-neutral rendering of the specification document (section 18). Rendering writes only the spec file; it changes no finding state by itself and is re-runnable.

## 17. Run Improvement Delta

Phase 1 contract (invocation-boundary coverage; nothing stronger is claimed): delta generation and missing-delta verification are invocation-driven. AT EVERY ALF synthesis or verification invocation, ALL terminal governed runs to date are checked: each either has its Run Improvement Delta or is reported then as lacking one (Tier 1 lifecycle_failure candidate). Coverage is therefore complete AS OF the most recent ALF invocation; between invocations, no coverage exists and none is claimed - a terminal run followed by no ALF invocation has neither a delta nor a report, and a regression test pins exactly this case. The authority's every-run outcome is reached through this mechanism plus operator process (invoking ALF as part of run practice); automatic wiring into the terminal-summary path is a Phase 2 candidate and is NOT claimed here.

Mechanics: the delta generator runs at run boundaries (invocation-driven, same trigger as observation capture) and writes alf/deltas/rid-<run-id>.json inside an operation-journal transaction. DELTA INPUT SNAPSHOT (versioned, immutable, SELF-SUFFICIENT): at FIRST generation, and inside the same transaction, the generator persists alf/deltas/rid-<run-id>.input.json = {snapshot_version: 2, run_id, membership_rule (the deterministic predicate defining what belongs to this run: every OCCURRENCE (per-run observation record, section 5) whose run_id equals this run_id, and every attribution and finding revision whose run_id equals this run_id, with all delta_report attribution lines EXPLICITLY EXCLUDED so generation output never feeds back into generation input, each set canonically ordered by id), occurrences: ordered [{occurrence_id, observation_id, run_id, line_sha256}], observations: ordered [{observation_id, sha256}] (the fact observations the occurrences cite), attributions: ordered [{attribution_id, attribution_type, line_sha256}], finding_revisions: ordered [{entry_id, revision_no, revision_sha256}], baselines: ordered [{entry_id, baseline_tier, baseline_score, baseline_model_version, baseline_status, baseline_cumulative_waste (the six named raw counters cumulative_operator_minutes, cumulative_execution_delay, cumulative_token_estimate, cumulative_api_attempts_wasted, cumulative_tool_attempts_wasted, cumulative_council_attempts_wasted, each an integer with absent = 0)}] capturing, for every finding this run touches, the PRE-RUN state - the finding's state as of the revision immediately before this run's FIRST revision for that finding - needed for the old-vs-new fields}. MULTI-REVISION REDUCTION: when a finding has several revisions in one run, the delta endpoint is the revision with the highest revision_no bearing this run_id; intermediate revisions are represented only through that endpoint (old from the baseline, new from the endpoint), never as separate entries. Every manifest entry is a content-addressed IMMUTABLE REFERENCE (sha256 / line_sha256 / revision_sha256) into the append-only stores; the snapshot is serialized canonically and its sha256 is input_snapshot_sha256, recorded in the delta's anchors block. PER-FIELD DERIVATION (each delta field is a pure function of the snapshot alone): new_observations from the occurrence set (fact observations first seen this run), recurrences from occurrences of pre-existing facts; new_findings, observations_merged_into_existing, regressions_detected, and cumulative_waste_changes from the attributions partitioned by attribution_type; findings_priority_changed from finding_revisions compared against baselines (old_tier and old_score from the baseline, new from the endpoint revision), with EXACTLY ONE entry per finding per run and entries stably ordered by entry_id; cumulative_waste_changes carries one entry per counter-bearing finding per run, ordered by entry_id; released_fixes_revalidated and items_requiring_operator_review from the revision set plus baselines. On any rerun the generator RESOLVES the stored snapshot by input_snapshot_sha256 and RE-READS every referenced payload from the immutable stores, hash-verifying each; a missing or divergent reference FAILS CLOSED (Tier 0 durable-record-integrity), and no delta field is ever computed from live heads or the live ledger. Delta deterministic content is a PURE FUNCTION of this snapshot. Idempotence and rerun semantics (deterministic, timestamp-safe): generated_at is the FIRST successful generation time and anchors reflect the state at first generation; both are preserved verbatim on any rerun. A rerun for an existing run_id recomputes the deterministic content (every field except generated_at and anchors) FROM THE STORED SNAPSHOT - the identical logical input, never the live ledger or heads - and compares it to the stored delta's deterministic content: equal = verified no-op (file untouched, later global anchor movement never re-anchors an existing delta and is never divergence); different = REFUSED divergent rewrite, reported as a Tier 1 durable-record-integrity finding candidate (divergence against an immutable snapshot signals a defect). The MISSING-DELTA VERIFIER (part of alf-verify) lists terminal governed runs (from summaries) that lack a delta and reports each as a Tier 1 lifecycle_failure finding candidate, so gaps are detected and escalated rather than silently accepted.

Delta schema (alf_record_version 1): run_id; work_item_id; generated_at; new_observations [ids]; new_findings [entry ids]; observations_merged_into_existing [{observation_id, entry_id}]; findings_priority_changed [{entry_id, old_tier, old_score, new_tier, new_score, model_version, reason}]; released_fixes_revalidated [{entry_id, verification_evidence_ref}]; regressions_detected [{entry_id, evidence_refs}]; items_requiring_operator_review [entry ids with reasons]; cumulative_waste_changes [one entry per counter-bearing finding per run, ordered by entry_id, each {entry_id, per_counter: {counter_name: {delta, new_total}}}]; anchors {observations_index: {head_line_sha256, line_count}, ledger: {head_line_sha256, line_count}, journal: {head_line_sha256, line_count}, findings_revision_heads_sha256, input_snapshot_sha256, prev_delta_anchors_sha256} (the tamper-evidence chain of section 8; each of observations_index, ledger, and journal is a STRUCTURED anchor carrying both head_line_sha256 and line_count - empty-file sentinel is the sixty-four-zero-hex head with line_count 0 - so delta-anchor ancestry verification requires each recorded head to appear at exactly its recorded line_count position in the validated live chain, the same position-based proof the expected-head checkpoints use; ALL head values here - including the journal head - are the PRE-transaction heads as of before this delta's own op_begin, so the anchors are ACYCLIC per section 8 and never reference this transaction's own op_commit; this transaction's op_commit is anchored FORWARD by the next delta's pre-transaction journal head and by the journal's own per-line chain; input_snapshot_sha256 binds the delta to its immutable input snapshot and is the handle a rerun resolves; findings_revision_heads_sha256 is defined exactly as the sha256 of the canonical bytes of a sorted-by-entry_id array of {entry_id, history_line_count, head_line_sha256} over all finding histories, with the no-histories case defined as the sha256 of the canonical empty array; and delta-anchor verification uses the SAME ancestry proof as the section 8 expected-head checkpoints - each recorded head must appear at its recorded line position in the validated live chain, applied to every anchored file and to the aggregate finding-history set, including the first-delta case).

An empty delta is still written (all arrays empty, anchors populated) so a governed run with ALF capture invoked always has its delta record, and the missing-delta verifier detects every terminal governed run without one.
